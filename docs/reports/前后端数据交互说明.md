# SreAgent 前后端数据交互说明

本文描述当前 SreAgent 基于 AgentScope 2.0.1 的实时流式交互、ReAct 轮次构造、断线重连及历史回显逻辑。

## 1. 核心对象与边界

一次用户提问对应一次任务（也对应一个 `chat_turn` 和一个 Redis `turnId`）。前端为该任务创建：

- 一条用户消息；
- 一条 assistant 占位消息，即一个 SRE Agent 气泡；
- 一个气泡内可包含多轮 ReAct，每次模型调用对应一条 `ReActRound`。

`round-N` 的作用域是单次用户提问，不是整个会话。每个任务的首次 `ModelCallStartEvent` 均创建 `round-1`。

```ts
interface ChatMessage {
  id: string
  role: 'user' | 'assistant'
  content: string                 // 旧数据或无 rounds 时的兼容正文
  reasoning?: string              // 旧数据或无 rounds 时的兼容思考
  createdAt: string
  status?: 'streaming' | 'complete' | 'stopped' | 'error'
  tools?: ToolCallState[]         // 旧数据或无 rounds 时的兼容工具集合
  rounds?: ReActRound[]
  error?: string
  sourcePrompt?: string
}

interface ReActRound {
  id: string                      // round-1、round-2……
  index: number
  status: 'streaming' | 'model_complete' | 'complete' | 'error'
  content: string
  reasoning?: string
  tools: ToolCallState[]
}

interface ToolCallState {
  id: string                      // toolCallId
  name: string
  status: 'running' | 'completed' | 'error'
  input?: string
  result?: string
  resultState?: string
}
```

## 2. HTTP 接口

基础路径为 `/api/chat/sessions`，用户身份通过 `X-User-Id` 请求头传递。

| 接口 | 用途 |
|---|---|
| `POST /{sessionId}/messages` | 发送消息并返回 SSE 流 |
| `GET /{sessionId}/messages` | 加载已持久化的历史消息 |
| `GET /{sessionId}/stream/status` | 查询当前任务运行状态 |
| `POST /{sessionId}/stream/reconnect` | 从指定 offset 回放 Redis 事件并续流 |
| `POST /{sessionId}/stream/interrupt` | 中断当前 Agent 任务 |

发送消息示例：

```http
POST /api/chat/sessions/{sessionId}/messages
Accept: text/event-stream
Content-Type: application/json
X-User-Id: demo-user

{"message":"查询 qwen-plus 过去一小时 5xx 并分析根因","requestId":"request-uuid"}
```

## 3. 实时流式链路

```text
sendMessage
  → POST /messages
  → ChatController.sendMessage
  → ChatStreamService.startTurn
  → 后台 ChatStreamService.runGeneration
  → HarnessAgent.streamEvents
  → AgentEventSseMapper
  → Redis StreamEventStore
  → ChatStreamService.tail
  → SSE HTTP 响应
  → consumeSseStream
  → applyStreamEvent
  → ChatMessage.rounds
  → MessageList / ReActRoundView
```

### 3.1 前端发起与占位消息

`useChatWorkspace.sendMessage` 在请求成功前即把以下两条消息追加到当前会话的本地列表：

```text
USER:      用户输入，status=complete
ASSISTANT: 空气泡，status=streaming，rounds=[]
```

assistant 气泡由前端创建，不依赖 `AgentStartEvent`。因此已有历史消息不会被新任务覆盖；同一会话内的第二次提问会创建新的用户消息和新的 assistant 气泡。

### 3.2 后端生成与 Redis 缓冲

`ChatStreamService.startTurn` 用 `requestId` 作为 `turnId` 在 Redis 中登记运行状态，并在后台线程运行 `runGeneration`。HTTP 客户端断开不会终止该后台生成。

Redis key：

```text
events:{sessionId}:{turnId}  List，按顺序存储序列化后的 SsePayload
meta:{sessionId}:{turnId}    Hash，state、startedAt、hb
cur:{sessionId}              当前活跃 turnId
```

每一个 AgentScope `AgentEvent` 先经过 `ReActRoundTracker`，再由 `AgentEventSseMapper` 转为 `SsePayload` 并写入 `events` List。`tail` 从指定 offset 读取 List，转换成 SSE 下发。

### 3.3 ReAct 轮次编号

`ReActRoundTracker` 是 `runGeneration` 的局部对象，不是单例状态，因此不会跨会话或跨任务共享。

```text
AgentStartEvent
  → currentRoundId 为 null，不递增，不属于任何 ReAct 轮次

第一次 ModelCallStartEvent
  → roundIndex: 0 → 1
  → currentRoundId = round-1

本轮的思考、正文、工具调用、工具结果
  → 都携带 roundId=round-1

第二次 ModelCallStartEvent
  → roundIndex: 1 → 2
  → currentRoundId = round-2
```

工具结果在 `ModelCallEndEvent` 之后、下一次 `ModelCallStartEvent` 之前到达，因此继续使用当前 `roundId`，归属到发起该工具调用的轮次。

## 4. AgentScope 事件顺序与 SSE 映射

框架层典型多轮 ReAct 事件序列：

```text
AgentStartEvent

  ModelCallStartEvent
    ThinkingBlockStartEvent
    ThinkingBlockDeltaEvent × N
    ThinkingBlockEndEvent
    TextBlockStartEvent
    TextBlockDeltaEvent × N
    TextBlockEndEvent
    ToolCallStartEvent
    ToolCallDeltaEvent × N
    ToolCallEndEvent
  ModelCallEndEvent

  ToolResultStartEvent
  ToolResultTextDeltaEvent × N
  ToolResultEndEvent

  ModelCallStartEvent
    ... 第二轮思考、正文或下一次工具调用 ...
  ModelCallEndEvent

AgentResultEvent
AgentEndEvent
```

无工具调用时，`ModelCallEndEvent` 后可直接进入 `AgentResultEvent` 和 `AgentEndEvent`。

后端 `AgentEventSseMapper` 的映射如下。除任务开始前尚无轮次的事件外，轮次相关负载都带 `roundId`。

| AgentScope 事件 | SSE `event` / `SsePayload.type` | `data` 关键字段 |
|---|---|---|
| `ModelCallStartEvent` | `round_start` | `roundId` |
| `ModelCallEndEvent` | `round_model_end` | `roundId`、`inputTokens`、`outputTokens` |
| `ThinkingBlockStartEvent` | `thinking_start` | `roundId`、`blockId` |
| `ThinkingBlockDeltaEvent` | `thinking_delta` | `roundId`、`blockId`、`delta` |
| `ThinkingBlockEndEvent` | `thinking_end` | `roundId`、`blockId` |
| `TextBlockStartEvent` | `text_start` | `roundId`、`blockId` |
| `TextBlockDeltaEvent` | `text_delta` | `roundId`、`delta` |
| `TextBlockEndEvent` | `text_end` | `roundId`、`blockId` |
| `ToolCallStartEvent` | `tool_start` | `roundId`、`toolCallId`、`toolName` |
| `ToolCallDeltaEvent` | `tool_delta` | `roundId`、`toolCallId`、`delta` |
| `ToolCallEndEvent` | `tool_end` | `roundId`、`toolCallId`、`toolName` |
| `ToolResultStartEvent` | `tool_result_start` | `roundId`、`toolCallId`、`toolName` |
| `ToolResultTextDeltaEvent` | `tool_result_delta` | `roundId`、`toolCallId`、`delta` |
| `ToolResultEndEvent` | `tool_result_end` | `roundId`、`toolCallId`、`state` |
| `AgentResultEvent` | `result` | `roundId`、`text` |
| `AgentEndEvent` | `done` | 最后一个 `roundId`（如有） |
| `ExceedMaxItersEvent` | `error` | `roundId`、`code`、`maxIters` |
| 后台异常 | `error` | `message` |

SSE 线格式：

```text
id: <event-id>
event: text_delta
data: {"type":"text_delta","id":"<event-id>","data":{"roundId":"round-2","delta":"根因是"}}

```

`event` 与 JSON 内的 `type` 当前保持一致；前端优先使用 JSON 内的 `type`，缺失时才使用 SSE `event`。

## 5. 前端接收、累积与渲染

### 5.1 SSE 解析

`../../frontend/src/lib/sse.ts` 的 `consumeSseStream` 从 `ReadableStream` 读取字节流，以 `\n\n` 或 `\r\n\r\n` 切分 SSE 事件，解析：

```ts
interface StreamEnvelope {
  type: string
  id?: string | null
  data: Record<string, unknown>
}
```

解析后回调 `applyStreamEvent(sessionId, assistantId, state, eventName, envelope)`。

### 5.2 构造完整 assistant 对象

`applyStreamEvent` 从 `data.roundId` 得到目标轮次；若事件先于 `round_start` 到达，使用 `updateRound` 按该 ID 懒创建轮次。这使 Redis 回放只要保留事件顺序即可恢复结构。

| 前端收到的 type | 对 `ChatMessage.rounds` 的处理 |
|---|---|
| `round_start` | 创建或更新指定轮次，状态设为 `streaming` |
| `round_model_end` | 指定轮次状态设为 `model_complete` |
| `thinking_delta` | 追加到该轮 `reasoning` |
| `text_delta` | 追加到该轮 `content` |
| `tool_start` | 在该轮 `tools` 中新增 `running` 工具 |
| `tool_delta` | 按 `toolCallId` 追加工具 `input` |
| `tool_result_delta` | 按 `toolCallId` 追加工具 `result` |
| `tool_result_end` | 写入 `resultState`；状态为 `ERROR` 时工具标为 `error`，否则为 `completed` |
| `result` | 以最终 `text` 补全该轮 `content`，轮次设为 `complete` |
| `done` | 任务消息设为 `complete`，剩余 `streaming` / `model_complete` 轮次都设为 `complete` |
| `error` | 任务消息设为 `error`，保存错误描述 |

当前前端会安全忽略 `thinking_start`、`thinking_end`、`text_start`、`text_end`、`tool_end`、`tool_result_start`。这些事件已在后端下发，保留给后续实现更细的阶段状态展示；当前内容完整性依赖 Delta 事件和 `tool_result_end`。

`MessageList` 检测 `message.rounds` 非空时，在同一个 SRE Agent 头像下循环渲染 `ReActRoundView`：每轮独立显示标题、思考折叠框、工具输入/结果与 Markdown 正文。没有 `rounds` 的旧数据仍回退渲染顶层 `content`。

## 6. 收尾、中断与重连

### 6.1 收尾

`AgentResultEvent` 是应用层的回答完成锚点。`ChatStreamService` 收到它后立即：

1. 将最终文本（或累计正文）写入 `chat_turn.response_text`；
2. 将 Redis turn 标记为 `done`；
3. 继续让 AgentScope 流的记忆 flush 等尾部副作用完成。

这样前端不必等待 `AgentEndEvent` 之后的记忆处理。`AgentEndEvent` 会映射为 `done` SSE 事件；但由于 Redis turn 已在 `AgentResultEvent` 时标记为 `done`，tail 可能在后续 `AgentEndEvent` 写入缓冲前结束。前端因此同时具备兜底逻辑：SSE 连接自然结束且未收到 `done`/`error` 时，也会把 assistant 气泡标记为 `complete`。

### 6.2 中断

前端调用 interrupt 接口，后端通过 `agent.getDelegate().interrupt(userId, sessionId)` 定向中断会话。前端保留已到达内容并标记为 `stopped`。框架产生的 `GenerateReason.INTERRUPTED` 恢复提示不是实际回答，Mapper 不会将它作为 `result` 下发。

### 6.3 断线续传完整执行逻辑

本项目不使用浏览器 `EventSource` 的原生重连，也不使用 `Last-Event-ID`。前端通过 `fetch` 发起 `POST` 请求并手工解析响应体；续读游标是业务层的 Redis List 下标 `offset`，而不是 SSE 事件的 `id`。

核心原则是：**Agent 生成与 HTTP SSE 连接解耦。** 后台 `runGeneration` 持续生成并写 Redis；每一条 SSE 连接只是一条从 Redis 缓冲读取并下发的 `tail`。因此客户端断开不会取消模型调用。

```text
                 ┌──────────────────────────────────────────────┐
                 │ runGeneration（后台生成任务）                 │
                 │ Agent 事件 → 映射 SsePayload → RPUSH Redis   │
                 └─────────────────────┬────────────────────────┘
                                       │ 事件缓冲
                                       ▼
                     events:{sessionId}:{turnId}（Redis List）
                                       │ LRANGE offset -1
                                       ▼
                 ┌──────────────────────────────────────────────┐
                 │ tail（每条 SSE 连接一个读取任务）             │
                 │ 回放积压事件 + 轮询增量事件 → SseEmitter      │
                 └─────────────────────┬────────────────────────┘
                                       ▼
                              浏览器 fetch SSE 流
```

#### 6.3.1 首次发送：登记、后台生成与首条 tail

前端 `useChatWorkspace.sendMessage` 先在 React 状态中创建用户消息和 assistant 占位气泡，再调用 `POST /{sessionId}/messages`。

后端 `ChatController.sendMessage` 的执行顺序：

1. `ChatService.prepare` 同步校验会话归属、会话是否 `OPEN`、`requestId` 是否重复；此步骤使用 MySQL，失败时直接返回 404/409，而不是在 SSE 中发送错误。
2. `ChatStreamService.startTurn` 将 `requestId` 复用为 `turnId`，同步调用 `StreamEventStore.register`：
   - 写入 `meta:{sessionId}:{turnId}` Hash：`state=running`、`startedAt`、`hb`；
   - 写入 `cur:{sessionId}` String，内容为本轮 `turnId`；
   - 给两个 key 设置流缓存 TTL。
3. `startTurn` 把 `runGeneration` 投递到 `chatStreamExecutor` 后立即返回，不等待模型输出。
4. 控制器创建无限超时的 `SseEmitter`，调用 `attach(..., offset=0)`；`attach` 再投递 `tail` 任务。首次 tail 与生成任务并行：一个写 Redis，一个读 Redis 并下发。

`runGeneration` 启动后先抢占会话租约：`SET lease:{userId}:{sessionId} {ownerToken} NX PX {leaseSeconds}`。取得租约后逐个消费 Agent 事件，映射为 `SsePayload` 并执行：

```text
RPUSH events:{sessionId}:{turnId} {payloadJson}
EXPIRE events:{sessionId}:{turnId} {ttl}
```

由此形成按发生顺序排列、可供任何后续连接回放的事件磁带。

#### 6.3.2 tail 如何读取、推送与结束

`ChatStreamService.tail` 持有本地 `offset`，循环执行：

1. `HGETALL meta:{sessionId}:{turnId}`，读取 `state / startedAt / hb`；
2. `LRANGE events:{sessionId}:{turnId} {offset} -1`，取得尚未发送的所有事件；
3. 每发送一个事件后本地 `offset++`；
4. 若状态为 `running` 且没有终态，休眠 `pollMillis` 后继续轮询；默认是 150ms。

状态处理如下：

| Redis/派生状态 | tail 行为 |
|---|---|
| `running` | 继续回放并轮询新增事件 |
| `done` / `failed` | 已读取本次区间后结束 emitter |
| `stale` / `none` | 下发 `error` 事件“本轮生成已中断或丢失，请重试”，然后结束 emitter |

`emitter.send()` 因浏览器关闭、网络断开而抛出 `IOException` 时，tail 仅标记该连接 `disconnected` 并结束 emitter。它不会关闭 `runGeneration` 的事件流，后台仍继续追加 Redis 事件并最终持久化回答。

#### 6.3.3 心跳、TTL 与 stale 判定

生成任务启动一个定时心跳，默认每 5 秒调用 `StreamEventStore.heartbeat`：

```text
HSET   meta:{sessionId}:{turnId} hb {now}
EXPIRE meta:{sessionId}:{turnId}   {ttl}
EXPIRE events:{sessionId}:{turnId} {ttl}
EXPIRE cur:{sessionId}             {ttl}
```

心跳有两个目的：

- 长时间模型调用期间持续延长 Redis 缓冲的生存期，避免尚未完成的流在默认 30 分钟 TTL 到期后丢失；
- 让 `status` 能识别生成任务是否失活。若 `state=running` 且 `now - hb > staleAfterSeconds`（默认 30 秒），服务端返回派生状态 `stale`，避免前端无限等待。

正常结束时，收到 `AgentResultEvent` 即先将最终文本或已累积正文写入 `chat_turn.response_text`，再将 `meta.state` 更新为 `done`；异常且未完成时追加 `error` payload 并更新为 `failed`。上述终态 key 不会立即删除，仍保留到 TTL 过期，使断线客户端可以查询最终状态。

流缓存 key 的默认前缀为 `sre:stream:`，默认 TTL 为 30 分钟；会话租约 key 默认前缀为 `sre:session:lease:`，TTL 为 900 秒。流缓存由心跳续期；当前会话租约没有续期机制。

#### 6.3.4 刷新页面后的续读

刷新会清空 React 内存状态。会话激活后，前端按以下顺序执行：

1. `loadSessionMessages(sessionId)`：从历史接口加载已持久化的消息；正在生成的半截正文此时可能尚未落库。
2. `resumeIfRunning(sessionId)`：请求 `GET /{sessionId}/stream/status`。
3. 服务端先读取 `GET cur:{sessionId}` 得到最近登记的 `turnId`，再读取该轮 `meta`，返回 `running`、`done`、`failed`、`stale` 或 `none`。
4. 只有状态为 `running` 且存在 `turnId` 时，前端新建一个空的 streaming assistant 占位气泡，并调用 `runReconnect`。
5. `runReconnect` 首次调用 `POST /{sessionId}/stream/reconnect`，请求体为 `{ turnId, offset: 0 }`。因此页面刷新会从本轮 List 的第 0 项开始全量回放 Redis 缓冲的思考、正文、工具等事件，再持续读取新事件。

`reconnect` 在建立 emitter 后再次查询指定 `turnId` 的状态，以处理 status 检查与实际建立连接之间的竞态：

- 仍为 `running`：调用 `attach`，由新 tail 从请求 offset 回放并增量轮询；
- 已变为 `done`、`failed`、`stale` 或 `none`：调用 `attachStatusOnly`，仅发送 `reconnect_status` 后关闭流。

前端收到 `reconnect_status` 时会删除占位气泡、清空当前会话内存消息并重新调用历史接口；这避免已完成轮次空转到 TTL 过期。

#### 6.3.5 同一页面中的重试行为

`runReconnect` 在一次续流生命周期内维护 `offset`。每消费一个正常 SSE 负载即 `offset++`；若 reconnect 的 HTTP 请求或 SSE 读取异常，则按 1s、2s、4s、5s……退避重试，最多 6 次。下一次请求携带更新后的 offset，只读取尚未应用的 List 项，避免同一页面内重复拼接文本。

首次 `sendMessage` 的 SSE 读取异常当前会直接将气泡标为错误；自动的退避续读逻辑位于 `runReconnect`，主要由刷新后的 `resumeIfRunning` 触发。

#### 6.3.6 中断与断开不是同一件事

- **连接断开/刷新**：仅关闭对应 tail；后台生成继续，事件继续写 Redis，之后可 reconnect。
- **用户主动停止**：前端先请求 `POST /stream/interrupt`，后端调用 `agent.getDelegate().interrupt(userId, sessionId)`，再中止本地 fetch。应用层累积的已生成正文会在收尾时写入 `chat_turn.response_text`，供历史回显兜底。

#### 6.3.7 当前实现边界

- `offset` 是 Redis List 下标，不是 SSE `id`。SSE payload 虽带事件 `id`，但前端从未发送 `Last-Event-ID`；不能将其视为精确补发游标。
- 页面刷新从 `offset=0` 全量重放；同页重试才使用递增 offset。若需要多标签页、事件裁剪或严格幂等去重，应新增单调 `eventSeq` 并让前端按该序号去重。
- Redis 流缓存 TTL 到期后，或心跳无法刷新导致 `stale` 后，半截流无法再从 Redis 回放；只能依赖已持久化历史。
- `register` 在获取会话租约之前执行。并发提交不同 `requestId` 时，后登记的轮次会覆盖 `cur:{sessionId}`，即使它随后获取租约失败。因此 `cur` 表示“最近登记的轮次”，不严格等同于“实际持锁生成中的轮次”。

## 7. 历史消息回显

历史回显不读取 Redis，而读取 `agentscope_sessions` 表中 `state_key=agent_state` 的 `state_data`。

AgentScope 的 `context` 典型结构：

```text
USER:      用户问题
ASSISTANT: 第 1 次模型调用产生的 thinking / text / tool_use
TOOL:      对应 tool_result
ASSISTANT: 第 2 次模型调用产生的 thinking / text / tool_use
TOOL:      对应 tool_result
ASSISTANT: 最终分析正文
USER:      下一次用户问题
```

`SessionHistoryService` 的解析逻辑：

1. 预扫描所有 `TOOL` 内容块，按 `tool_result.id` 建索引；
2. 遍历 `context`；
3. 遇到 `USER` 时，先将前一个 USER 之后收集到的多个 `ASSISTANT` 轮次聚合成一个 assistant `HistoryMessage`，再追加用户消息；
4. 遇到正常 `ASSISTANT` 时，收集 `thinking`、`text` 和 `tool_use`，建立一个 `ReActRound`；工具结果通过相同 `toolCallId` 从索引回填；
5. 遍历结束后再提交最后一个任务；
6. 若末尾是中断恢复提示，则从 `chat_turn.response_text` 追加一个 `stopped` assistant 消息作为兜底。

返回的 JSON 与前端 `ChatMessage` 结构兼容，前端不再重新分组，只直接赋入会话的消息列表并由 `MessageList` 按 `rounds` 渲染。

## 8. 关键实现文件

## 9. 约束与注意事项

- 正确事件名是 `ModelCallStartEvent` / `ModelCallEndEvent`，不是 `ModelStartEvent` / `ModelEndEvent`。
- `roundId` 来自应用层计数器，不是 AgentScope 原生字段；只能由 `ModelCallStartEvent` 递增。
- 不要在 `AgentEventSseMapper` 单例中保存轮次可变状态，否则并发任务会发生串扰。
- 不要把 `AgentStartEvent` 计入轮次，否则首次模型调用会错误成为 `round-2`。
- 工具结果必须归属到下一次 `ModelCallStartEvent` 前的当前轮次。
- 改动 SSE type、`roundId` 或 `ReActRound` 时，需要同步调整 Mapper、历史解析、TypeScript 类型、`applyStreamEvent` 和 UI，否则实时与回显结构会不一致。
- 当前历史数据源为 `state_data`；发生上下文压缩后，早期细节可能被摘要替代，无法完整恢复。
